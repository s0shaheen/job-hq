# Unbreakable bot+human Google Sheet vs. Airtable/Notion cockpit — verified findings (July 2026)

Scope: job-search HQ spreadsheet. Bots = Python gspread from GitHub Actions (hourly/daily): append rows, update status columns, read config. Humans = owner on Sheets phone app + non-technical assistant: sort, filter, insert/rename/reorder columns, add tabs, edit freely. Requirement: no normal human spreadsheet action may silently break the automation.

---

## 1. What humans actually break (failure-mode inventory)

| Human action | What it breaks if bot is naive |
|---|---|
| Sort rows | Any cached row number; a write lands on the wrong application |
| Insert/reorder columns | Any hardcoded A1 column letter |
| Rename a column header | Name-based addressing (`get_all_records` keys) |
| Add a second blank/duplicate header | `get_all_records` **raises** `GSpreadException` — whole run dies |
| Rename/duplicate a tab | Lookup by worksheet title |
| Leave a basic filter on | Shared state: hides bot-appended rows from everyone; filters are collaborative, filter views are not ([support.google.com/docs/answer/3540681](https://support.google.com/docs/answer/3540681?hl=en)) |
| Type below/inside a formula view | `#REF! "Array result was not expanded because it would overwrite data"` ([Makhrov, Medium](https://max-makhrov.medium.com/google-sheets-fixed-ref-error-array-result-was-not-expanded-because-it-would-overwrite-data-16f5c7c882de)) |
| Edit mid-bot-run | Read-modify-write race; the Sheets values API has **no compare-and-set/ETag primitive** (nothing in the [values guide](https://developers.google.com/workspace/sheets/api/guides/values) or REST reference offers conditional writes) |

Every one of these has a verified countermeasure below.

## 2. gspread (current: **6.2.1**, released 2025-05-14 — [PyPI](https://pypi.org/project/gspread/)) — verified from source

### 2.1 `get_all_records` exact semantics (read from [master worksheet.py](https://github.com/burnash/gspread/blob/master/gspread/worksheet.py))
- **No `expected_headers`:** duplicate headers in row 1 → `GSpreadException: "the header row in the worksheet contains duplicates"`. Two or more **blank** headers count as duplicates of `""` — so an assistant adding two unnamed columns kills every naive read ([issue #1007](https://github.com/burnash/gspread/issues/1007), [#986](https://github.com/burnash/gspread/issues/986)).
- **With `expected_headers`:** they must be unique AND a subset of actual headers; duplicates *elsewhere* in the header row are then tolerated — but silently: records are built via `dict(zip(headers, row))` (`to_records` in [utils.py](https://github.com/burnash/gspread/blob/master/gspread/utils.py)), so **the last duplicate column wins and earlier ones vanish from the dict**. Silent data loss on read, no error.
- Behavior has churned across versions (5.11→5.12 broke `expected_headers` users — [issue #1352](https://github.com/burnash/gspread/issues/1352); redesign discussion [#1367](https://github.com/burnash/gspread/issues/1367)). **Pin the version.**
- Values are **numericised by default** (strings that look like numbers become int/float) — round-trip hazard for IDs/zip codes; disable with `numericise_ignore=['all']` ([API ref](https://docs.gspread.org/en/latest/api/models/worksheet.html)).
- Conclusion: `get_all_records` is acceptable only as a convenience read with `expected_headers`; **column addressing must come from your own header map** (§7 R3), not from this method.

### 2.2 Row lookup, appends
- `find(query, in_column=N)` / `findall` support exact strings and compiled regex, scoped to one column — the key-column row lookup primitive ([worksheet API](https://docs.gspread.org/en/latest/api/models/worksheet.html)). `find` returns `None` when absent.
- `append_row/append_rows(values, value_input_option=..., insert_data_option=..., table_range=...)` wraps `values.append`, whose documented behavior: the input range "is used to search for existing data and find a 'table'"; "values are appended to the next row of the table, starting with the first column of the table"; default **overwrites** data after the table unless `insertDataOption=INSERT_ROWS` ([values guide](https://developers.google.com/workspace/sheets/api/guides/values)). Anchor detection with `table_range="A1"`.
- `RAW` vs `USER_ENTERED`: `USER_ENTERED` "is parsed exactly as if it were entered into the Sheets UI" (date/number coercion — the "MARCH1" class of corruption); `RAW` inserts as-is ([same guide](https://developers.google.com/workspace/sheets/api/guides/values)).
- No optimistic concurrency anywhere in the values API → single-writer design + post-write verification are the only defenses.

### 2.3 Developer metadata — API yes, gspread **no**
- Sheets API supports metadata on spreadsheet/sheet/**row ranges/column ranges**; it "remains associated at those locations as they move around and the spreadsheet is edited" — documented example: metadata on row 5 follows the row to row 6 after an insert above; deleted with its object; queried via `developerMetadata.search` with `DataFilter`; limits 30,000 chars per spreadsheet + 30,000 per sheet; `DOCUMENT` vs `PROJECT` visibility ([metadata guide](https://developers.google.com/workspace/sheets/api/guides/metadata), [REST resource](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.developerMetadata)).
- **UNCERTAIN / undocumented:** whether row metadata follows data through a human **sort**. The guide documents insert/delete/move, never sort; a sort permutes cell values rather than moving dimensions, so the safe assumption is metadata does NOT follow sorted rows. I found no primary source either way — do not build row identity on it.
- **gspread has zero developer-metadata methods** (grepped master `worksheet.py`/`spreadsheet.py`: no `developerMetadata` anywhere). Workarounds exist: `Spreadsheet.batch_update(body)` is a raw passthrough to `spreadsheets:batchUpdate` (can send `createDeveloperMetadata`), and `HTTPClient.request()` is a generic authenticated HTTP method usable for the `developerMetadata:search` endpoint ([http_client.py](https://github.com/burnash/gspread/blob/master/gspread/http_client.py)). Verdict: usable for **column** anchors if you want belt-and-suspenders, but the header map makes it unnecessary.

### 2.4 Named ranges
- gspread natively supports `define_named_range`, `update_named_range`, `delete_named_range`, `Spreadsheet.list_named_ranges()`, and named ranges in `batch_clear`/range reads ([worksheet.py source](https://github.com/burnash/gspread/blob/master/gspread/worksheet.py)).
- Named ranges track **structural** edits (insert/delete shifts boundaries) but are positional under the hood — a sort moves data *through* a named range; it does not follow values. Good for anchoring a config block; wrong for row identity.

### 2.5 Protected ranges — the exact semantics matter
- gspread: `add_protected_range(name, editor_users_emails=[...], warning_only=False, ...)`, `delete_protected_range`, `Spreadsheet.list_protected_ranges(sheetid)` (source-verified).
- REST `ProtectedRange`: `warningOnly=true` means "every user can edit data in the protected range, except editing will prompt a warning asking the user to confirm the edit", and "**Editors are not supported with warningOnly protection**" ([ProtectedRange reference](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/sheets#ProtectedRange), [Apps Script Protection class](https://developers.google.com/apps-script/reference/spreadsheet/protection)). So warning-only = speed bump for humans, no effect on API writes (there is no dialog in the API path).
- Full protection restricts edits to the editors list (put the service account + owner there). *Likely but not stated verbatim in the REST docs:* full protection also rejects API writes from non-editor accounts — consistent with the permission model and community reports of scripts blocked by protections ([Docs Editors thread](https://support.google.com/docs/thread/93012587/protected-ranges-preventing-background-script-to-run-for-non-owners?hl=en)). Mark as high-confidence but inferred.
- **Critical interplay:** humans **cannot sort a range containing protected cells they can't edit** ([Docs Editors thread](https://support.google.com/docs/thread/10084409/is-it-possible-to-sort-google-sheets-if-it-has-protected-ranges-in-it?hl=en)). Fully protecting bot-owned *columns* on the shared tab would break the assistant's ability to sort — exactly the "normal spreadsheet behavior" that must keep working. Hence: **full protection only on whole tabs and the header row; warning-only on bot columns in shared tabs.** A frozen row 1 is excluded from sorts ("If your sheet includes a header row, freeze it" — [sort & filter help](https://support.google.com/docs/answer/3540681?hl=en)), so a fully-protected frozen header doesn't block sorting.

### 2.6 Data validation & the 2025 Tables API
- gspread `add_validation(range, ValidationConditionType.one_of_list, [values], strict=True, showCustomUi=True)` issues `setDataValidation` — dropdown chips on desktop *and* the phone app, `strict` rejects free-typed values (source-verified in worksheet.py).
- Sheets API gained **native table management on 2025-04-29**: `addTable`/`updateTable`/`deleteTable` via batchUpdate, typed columns (numeric, date, **DROPDOWN** backed by `ONE_OF_LIST`, checkbox, smart chip), and `AppendCellsRequest` with `tableId` that appends "to a table's end, automatically handling full rows and footers" ([tables guide](https://developers.google.com/workspace/sheets/api/guides/tables), [AppsScriptPulse](https://pulse.appsscript.info/p/2025/05/simplify-google-sheets-table-management-with-new-api-support/), [release notes](https://developers.google.com/workspace/sheets/release-notes)). Filters, filter views and protected ranges can be backed by tables. gspread has no wrapper yet — raw `batch_update` again. Converting the shared tracker to a Table is optional polish (typed columns + prettier UI); the append-by-tableId request is the most rename/sort-proof append primitive Google now offers.

### 2.7 Limits & quotas (all verified)
- **Spreadsheet size:** 10 million cells per spreadsheet ([2022 announcement](https://workspaceupdates.googleblog.com/2022/03/ten-million-cells-google-sheets.html)); April 2026: performance improvements GA (large-file open ~30% faster, filtering ~60% faster) plus an opt-in **beta doubling to 20M cells**, consumer accounts included ([Workspace Updates, Apr 2026](https://workspaceupdates.googleblog.com/2026/04/faster-performance-and-doubled-cell-limits-in-Google-Sheets.html)). At 30 applications/week × 50 columns, that's ~80 k cells/year — three orders of magnitude of headroom.
- **Sheets API quotas:** 300 requests/min/project and **60 requests/min/user/project, read and write separately; no daily cap**; 429 on breach; Google prescribes truncated exponential backoff; increases requestable in Cloud Console ([sheets/api/limits](https://developers.google.com/sheets/api/limits)). An hourly Action doing one `batch_get` + one `batch_update` uses <5% of one minute's user quota.
- gspread ships a ready-made backoff client: `gspread.service_account(filename=..., http_client=gspread.BackOffHTTPClient)` (exponential retry on 429; parameter verified in [auth.py](https://github.com/burnash/gspread/blob/master/gspread/auth.py), class in [HTTP client docs](https://docs.gspread.org/en/master/api/http_client.html)).
- **Apps Script, consumer @gmail.com:** triggers total runtime **90 min/day**, **20 installable triggers/user/script**, 6 min/execution, 20,000 UrlFetch calls/day, 100 email recipients/day ([Apps Script quotas](https://developers.google.com/apps-script/guides/services/quotas)). Plenty for an `onChange` tripwire that POSTs to ntfy when someone renames a header or deletes a column — but keep Apps Script as *alarm only*, never a load-bearing writer (silent auth-expiry and quota edges make it the least "never breaks" component).

## 3. Same tab vs. per-tab isolation

**Pure isolation (bot-owned raw tabs + human QUERY/FILTER view tabs)** is the textbook pattern, but it fails this scenario's requirement that humans *edit*: a QUERY/FILTER view is read-only in practice — edits inside the spill zone don't write back, and any value left in the spill path collapses the whole view to `#REF!` ("Array result was not expanded because it would overwrite data…", [Makhrov](https://max-makhrov.medium.com/google-sheets-fixed-ref-error-array-result-was-not-expanded-because-it-would-overwrite-data-16f5c7c882de)). Views are great for dashboards, wrong as the assistant's workspace.

**Verified hybrid (recommended):**
- **`ledger` tab — bot-only, append-only** (full-sheet protection, editors = service account + owner): every event the bot emits. Humans can look, can't touch. Mirrors the existing `applications-log.csv` single-writer discipline.
- **`tracker` tab — shared:** column A = immutable key (`app_id`/job URL, minted at intake). Bot-owned columns warning-only-protected and prefixed (e.g. `bot: last_status_check`); human columns free; header row 1 frozen + fully protected; status columns get strict `ONE_OF_LIST` dropdowns. Humans may sort/filter/insert columns at will — the bot re-resolves everything per run (§7).
- **`config` tab — fully protected** key-value pairs, read by key lookup in column A (never by cell coordinates).
- **`dash` view tab(s)** — QUERY over tracker/ledger for the owner's phone glance; nightly self-heal rewrites the formula if someone broke the spill.
- Humans who want a different ordering get **filter views** — personal, saved, and invisible to the bot and to each other ([filter views help](https://support.google.com/docs/answer/3540681?hl=en)); one 2-minute lesson for the assistant ("use the filter-view button, not Sort sheet") removes the biggest chaos source without depending on it for correctness.

## 4. Airtable as owner cockpit (verified July 2026)

- **Pricing/limits:** Free = 1,000 records/base, 5 editors, 1 GB attachments, **1,000 API calls/workspace/month**, 2-week revision history; Team = **$20/user/mo annual ($24 monthly)**, 50,000 records/base, 20 GB, **100,000 API calls/month** (over-cap throttles to 2 rps until month reset); Business = **$45/user/mo annual ($54 monthly)**, 125,000 records/base, 100 GB, unlimited API calls ([support: plans](https://support.airtable.com/docs/airtable-plans), [support: API call limits](https://support.airtable.com/docs/managing-api-call-limits-in-airtable), [airtable.com/pricing](https://airtable.com/pricing)). Record caps are cumulative across tables in a base. At 20-30 apps/week the Free record cap is ~9-12 months of runway and the Free API cap (≈33 calls/day) is below an hourly bot's floor → **realistic cockpit cost is Team, $240/yr**.
- **API:** 5 requests/sec/base, 50 rps per token; 429 then 30-second lockout ([rate limits](https://airtable.com/developers/web/api/rate-limits)). **Schema identity is Airtable's headline advantage:** `tbl…`/`fld…`/`rec…` IDs are immutable; official docs recommend table IDs over names for stability, `returnFieldsByFieldId` returns records keyed by field ID, and formulas accept field IDs ([list-records docs](https://airtable.com/developers/web/api/list-records), [finding IDs](https://support.airtable.com/docs/finding-airtable-ids)) — renames can never break an ID-addressed integration, which is precisely the property Sheets must be *engineered* to approximate. (Field-ID support in the `sort[]` parameter isn't explicitly documented — minor, uncertain.)
- **Webhooks:** expire **7 days** without a refresh call, silently; pings carry no payload (separate fetch, payloads retained 7 days) — a sync consumer needs its own keep-alive cron ([webhooks overview](https://airtable.com/developers/web/api/webhooks-overview), [refresh endpoint](https://airtable.com/developers/web/api/refresh-a-webhook), [field guide](https://www.getreportio.com/blog/airtable-webhooks-guide)).
- **Mobile (the cockpit's whole job) is Airtable's weak leg:** official docs list missing layout types in mobile Interfaces (Blank, Timeline, Record Review, Record Summary) and broad desktop/mobile feature gaps ([mobile interfaces](https://support.airtable.com/docs/mobile-interfaces-in-airtable), [feature differences](https://support.airtable.com/docs/differences-between-the-desktop-and-mobile-versions)); community/App-Store reports through 2025 describe iOS/Android parity chaos, mid-use refreshes losing unsaved edits, and slowness at tens of thousands of records ([community](https://community.airtable.com/interface-designer-12/mobile-issues-39175)). Interfaces exist on all plans (1 published interface/base on Free, 3 on Team per third-party 2026 pricing guides — [noloco](https://noloco.io/blog/airtable-pricing), [tinycommand](https://tinycommand.com/blogs/airtable-pricing-explained); *not confirmed on the official page, mark uncertain*). Forms exist on Free with cosmetic limits.
- **No native live sync from Google Sheets** — built-in integration is one-time import; continuous sync means your own API code or a third-party subscription (Whalesync, Data Fetcher…) ([community confirmation](https://community.airtable.com/other-questions-13/sync-data-with-google-sheets-16476)).

## 5. Notion as owner cockpit

- API: average **3 requests/sec** per integration with modest bursts, 429 + `Retry-After`; payload caps (1,000 blocks/500 KB per request, 2,000-char rich text, 100-item relation writes) ([request limits](https://developers.notion.com/reference/request-limits)).
- **Churn risk demonstrated:** the **2025-09-03 API version** restructured databases into multi-source databases — `/v1/databases/:id/query` superseded by `/v1/data_sources/:id/query`, database IDs alone no longer sufficient, Search API filter values renamed; Zapier/Retool integrations broke and required migration ([upgrade guide](https://developers.notion.com/docs/upgrade-guide-2025-09-03), [FAQ](https://developers.notion.com/docs/upgrade-faqs-2025-09-03)). A personal sync bridge inherits this maintenance tax.
- Mobile: consistently reviewed as laggy for database editing on phones ("editing tables on a phone is miserable"), with databases slowing past ~5,000 records due to client-side loading ([2025-26 reviews](https://hackceleration.com/notion-review/), [research.com](https://research.com/software/reviews/notion)). Fine as a reading surface, poor as a data cockpit, and it does nothing for the assistant.

## 6. Is a two-surface sync worth the seam?

No. The seam itself becomes the least-reliable component and the only one nobody notices failing: custom sync code (no native Sheets↔Airtable sync), webhook keep-alive crons that die silently after 7 days, Notion API version migrations, and — worst — **conflict semantics** the moment the owner edits in the cockpit while the assistant edits the Sheet (two-way sync = two sources of truth = the exact "silent corruption" this project bans). Every added surface also doubles the schema-drift audit area. The owner's phone needs: push alerts (ntfy already does this), a glanceable status board (the `dash` QUERY tab in the Sheets app, or an Artifact/GitHub-Pages board the bot regenerates), and occasional edits (Sheets mobile app on the tracker, with dropdown chips). If a prettier cockpit is ever genuinely wanted, the only sane shape is a **one-way, bot-pushed, read-only mirror** (Actions job upserts to Airtable Team keyed by `app_id` field IDs): the mirror is then a disposable projection whose total failure loses nothing — but it costs $240/yr plus a second schema to maintain for marginal benefit over the dash tab.

## 7. The bot-side coding rules that make human chaos safe

1. **Pin gspread** (`gspread==6.2.1`) — header-handling semantics have broken users across minor versions ([#1352](https://github.com/burnash/gspread/issues/1352)).
2. **Address tabs by immutable `sheetId` (gid)**, stored in bot config: `ss.get_worksheet_by_id(gid)` (source-verified method). Tab renames and "Copy of…" duplicates become harmless.
3. **Rebuild a header map every run:** read row 1, `strip()` each cell, assert every bot-required header exists **exactly once**, derive column indices, convert with `rowcol_to_a1`. Never hardcode column letters; never rely on column order; never write based on yesterday's map.
4. **Fail loud, never guess:** any header-map or key-lookup anomaly (missing/duplicate/blank required header, key not found, two rows with same key) → abort the run and push ntfy with the exact anomaly. A skipped run is recoverable; a guessed write is corruption.
5. **Row identity = immutable key column** (`app_id`/job URL, column A, minted at intake). Locate rows with `ws.find(key, in_column=1)` **at write time, per write**; row numbers must never survive across API calls because a human may sort mid-run. There is no compare-and-set in the Sheets API, so after each write, `batch_get` the key cell + written cells in one call and verify; on mismatch re-resolve and retry once, then alert.
6. **Appends:** `append_rows(values, value_input_option="RAW", insert_data_option="INSERT_ROWS", table_range="A1")` — documented table detection + INSERT_ROWS prevents clobbering anything below; RAW prevents `USER_ENTERED` date/number mangling. Write full rows aligned to the *current* header map, blank-padding bot-unknown columns. (Optional upgrade: convert tracker to a native Table and append via `AppendCellsRequest{tableId}`.)
7. **Reads:** prefer `batch_get` + your own header map; if using `get_all_records`, always pass `expected_headers=[...]` and `numericise_ignore=['all']`, and remember residual duplicate headers silently collapse last-wins — rule 3's assert is the real guard.
8. **One writer per cell:** columns are bot-owned or human-owned, never both; the bot never writes human columns. Bot-owned columns get **warning-only** protection (full column protection would block humans from sorting the tab — verified interplay) plus a `bot:` header prefix.
9. **Protection recipe:** header row = frozen + **full** protection (editors: owner + service account; frozen rows are excluded from sorts); `ledger` and `config` tabs = full-sheet protection; shared-tab bot columns = warning-only.
10. **Status fields = strict dropdowns:** `add_validation(..., ValidationConditionType.one_of_list, STATUSES, strict=True, showCustomUi=True)`; the bot validates against the same enum in code. Assistant gets chips on mobile; free-typed states become impossible.
11. **Config by key lookup, not coordinates:** 2-column protected `config` tab, `find("key", in_column=1)` → read column B; or a named range (survives insert/delete shifts, but positional under sorts — the protected tab makes sorts impossible anyway).
12. **Nightly self-heal job (idempotent):** re-assert protections (`list_protected_ranges` → repair), validations, frozen row, header names against a schema constant, and rewrite dash-tab formulas; diff-and-alert anything unexpected. This turns schema drift from silent corruption into a next-morning notification.
13. **Quota/backoff hygiene:** one `batch_get` for all reads + one `values.batchUpdate` for all writes per run; construct the client with `http_client=gspread.BackOffHTTPClient`; you'll idle at <5% of the 60 req/min/user quota.
14. **Nightly snapshot to git:** export each tab as CSV into the repo from the same Action. Sheets version history is the second line of defense; a diffable snapshot the owner controls is the first. Restores from any human catastrophe without a Mac.
15. **Do not build on developer metadata for rows:** gspread has no wrapper (raw `batch_update`/`HTTPClient.request` only) and its behavior under human sorts is undocumented (unverified — assume it stays behind). Header map + key column already deliver rename/reorder/sort immunity with zero exotic dependencies.
16. **Tripwire (optional):** one Apps Script installable `onChange` trigger POSTing structural-change alerts to ntfy — consumer quotas (20 triggers/script, 90 min/day, 20k UrlFetch/day) are orders of magnitude above need; keep it alarm-only, never a writer.

**Marked uncertain:** developer-metadata-under-sort (undocumented); REST-level statement that full protection rejects non-editor API writes (inferred + community-corroborated, not found verbatim); Airtable per-plan published-interface counts (third-party pricing guides only); Airtable `sort[]` field-ID support.

## RECOMMENDATION

Keep the Google Sheet as the single source of truth and the single surface — don't add Airtable or Notion. The assistant requirement pins Sheets anyway, and a second synced surface fails the "never breaks" bar on verified grounds: no native Sheets sync (custom seam code), Airtable webhooks that silently die after 7 days, Notion's 2025-09-03 breaking API migration, Airtable's weak mobile app, and two-way-sync conflict semantics that reintroduce silent corruption; Airtable's genuinely superior primitive (immutable tbl/fld/rec IDs) buys nothing once the Sheet is addressed correctly. Instead, make human chaos structurally safe: bot-only append `ledger` tab and `config` tab under full protection, a shared `tracker` tab where row identity is an immutable key column (job URL/app_id) and column identity is a per-run header map resolved from a fully-protected frozen header row, tabs addressed by gid, warning-only protection plus strict dropdown validation on bot-owned status columns (full column protection would block human sorting), and a QUERY dash tab for the owner's phone. Bot rules: pin gspread 6.2.1, find-by-key at write time with read-back verification (no cached row numbers, since Sheets has no compare-and-set), RAW + INSERT_ROWS appends, BackOffHTTPClient, batch reads/writes, and fail-loud-to-ntfy on any schema anomaly instead of guessing. Add the nightly self-heal + CSV-snapshot-to-git job — that single Action turns every remaining failure mode into a next-morning alert with a one-command restore. If a prettier phone cockpit is ever truly wanted, the only architecture worth considering is a one-way, bot-pushed, read-only Airtable mirror (Team, ~$240/yr) whose total loss costs nothing — but try the hardened Sheet plus ntfy first; at 10-30 applications/week it covers the owner-on-phone job at zero marginal cost and zero new failure surface.
