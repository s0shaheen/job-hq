# Phone-first editing for a RenderCV resume — findings (July 2026)

Goal restated: owner tweaks a bullet / reorders bullets / changes a phrase from his phone in <2 min; PDF re-renders automatically and lands in Google Drive; repo YAML stays the single source of truth; Mac may be asleep; no AI session.

## Ranked summary

| Rank | Option | Zero-drift | Phone UX | Setup | Ongoing maintenance |
|---|---|---|---|---|---|
| 1 | GitHub mobile app edit → GitHub Action renders → Drive upload | Perfect (repo is the only surface) | Adequate: raw YAML in the app's text editor; reorder = cut/paste | ~1–2 hrs | Near zero (pin rendercv version; one long-lived Google credential) |
| 2 | Tiny custom form editor (Vercel) committing via GitHub API → same Action | Perfect (commits to same repo; comment-preserving YAML lib) | Best possible: per-bullet fields + drag reorder | ~1–2 days build | Low but real (a small app you own) |
| 3 | RenderCV App (rendercv.com, hosted) | **Broken by design today**: GitHub sync is app→repo *backup*, so the app becomes the source of truth, in its own repo layout | Likely best-in-class (form editor, "any device") | Minutes | Vendor risk: solo-maintainer SaaS with open rendering bugs |
| 4 | Typst.app web editor | **Fatal**: edits generated `.typ`, not the YAML; manual pull/push git sync | Poor on phones (undocumented; VS-Code-class editor) | Low | N/A — reject |

## 1. RenderCV App (rendercv.com / app.rendercv.com)

**What it is now.** The hosted companion to the open-source CLI, relaunched as an "AI-native resume builder" ([rendercv.com](https://rendercv.com)). Marketing bullets on the homepage: "Industry-standard templates", "**Bring your existing CV** — Upload your CV and keep going", "AI career assistant", "**Form editor or YAML** — Simple enough for anyone. Powerful enough for engineers", "Multilanguage support". The page bundle loads Monaco editor, i.e., a real code editor for the YAML view. Sign-in is Google or GitHub OAuth only ([ToS](https://rendercv.com/terms-of-service)).

**Pricing (verified from [rendercv.com/pricing](https://rendercv.com/pricing), July 2026).** "One plan. Everything included. Pay your way": **$15/mo monthly, $10/mo quarterly ($31 billed every 3 months), $5/mo annual**, with a free trial; payments via Polar (merchant of record, per ToS). Paid plan includes: "Unlimited PDF downloads · AI that reads, edits, and improves your CV · Job-specific cover letter generation · Shareable public links · Search jobs and tailor your CV to match · **GitHub sync: your CVs backed up as a repository**". Free plan: "limited features and a storage limit of up to 6 CVs" (ToS); PDF downloads are implied limited on free (unlimited is a paid bullet). Full-account ZIP export exists (YAML + PDFs + Typst sources, per homepage FAQ).

**The zero-drift problem.** The only public description of GitHub sync is *backup direction* — "your CVs backed up as a repository." Nothing indicates it can adopt an existing repo with his layout (`resume/base.yaml` + separate `resume/design.yaml` + Makefile + `applications/` flow) or do two-way sync. Adopting the app means migrating the source of truth into the app and demoting the repo to a mirror — the opposite of the requirement. **Uncertain / needs a 15-minute free-account test:** whether pasting his full cv.yaml + custom harvard design renders identically, which rendercv engine version the app runs, and the exact repo layout GitHub sync produces.

**Reliability signals (matters for "never breaks").** The maintainer told HN on 2025-12-21 the web app was "a bit outdated. We'll update it at some point" ([HN thread](https://news.ycombinator.com/item?id=46344616)); it has since been revamped (blog cadence every ~2 days in June 2026). But the app's public [issue tracker](https://github.com/rendercv/rendercv-app) (code is closed-source; repo is issues-only) shows: site down (Feb 2026, #9), photo-URL error (Mar 2026, #10, open), **"PDF preview is not working" (Apr 2026, #11, still open)**. An independent 14-day review (Feb 26, 2026) lists cons: "design themes break frequently, bugs rarely fixed", unused AI credits expire monthly, slow support, and notes a native mobile app "coming soon" ([resumejudge.com](https://resumejudge.com/blog/rendercv-review/)). Also relevant: the project explicitly does **not** follow SemVer — a user reported his CV breaking after 3–4 months of engine changes and the maintainer confirmed intentional compatibility breaks within v2.x (HN thread). Verdict: great UX ceiling, but drift-by-design plus vendor fragility → not the primary path today; re-check in ~6 months for two-way sync.

## 2. GitHub-native flow (recommended)

**Phone editing surface — verified.** The GitHub mobile app (iOS/Android) edits any text file: Browse code → file → top-right menu → edit → commit directly to a branch or via new branch/PR ([changelog Nov 2022](https://github.blog/changelog/2022-11-15-github-for-ios-edit-files-from-browse-code/), [product post Mar 2023](https://github.blog/news-insights/product-news/file-editing-on-github-mobile-keeps-leveling-up/)). It is a plain text editor (no YAML validation — CI must be the validator). Editing on github.com in a mobile browser also works. **github.dev / vscode.dev is not a phone option**: technically loads but widely reported unusable on phone-size screens (keyboard covers half the viewport, gesture conflicts) — fine on iPad with keyboard only ([vscodemobile.com](https://vscodemobile.com/news/vscode-mobile-ios), [microsoft/vscode#85254](https://github.com/microsoft/vscode/issues/85254)). Nicer optional editor: **Working Copy** iOS git client — clone/edit/commit free, **push requires the one-time Pro unlock** (~$19.99–$35.99 depending on period/source — approximate) ([workingcopy.app manual](https://workingcopy.app/manual/purchase/)).

**Headless render in Actions — verified end-to-end.** The official template [rendercv/rendercv-pipeline](https://github.com/rendercv/rendercv-pipeline) runs on `ubuntu-latest` + `actions/setup-python@v5` (python 3.12) + `pip install` + `rendercv render`, uploads `rendercv_output` as artifact, and commits generated files back; its latest run succeeded 2025-11-12 ([workflow file](https://raw.githubusercontent.com/rendercv/rendercv-pipeline/main/.github/workflows/rendercv.yaml)). [PyPI rendercv 2.8](https://pypi.org/pypi/rendercv/json) (released 2026-03-21, matches his local `RenderCV v2.8`): `requires_python >=3.12`; the `[full]` extra pulls `typer, watchdog, typst>=0.14.8 (bundled Typst compiler wheel), rendercv-fonts (bundled fonts), packaging` — i.e., **pure-pip, no system packages, no LaTeX, fonts included → renders headless on ubuntu-latest with nothing but `pip install "rendercv[full]==2.8"`**. Because the project breaks compatibility within v2.x (HN, above; the official pipeline itself still pins `rendercv[full]==2.1`), **pinning `==2.8` to match the Mac install is mandatory** — same engine locally and in CI is itself a no-drift requirement. Workflow spine (mirrors his Makefile exactly):

```yaml
on: { push: { branches: [main], paths: ['resume/**'] } }
jobs:
  render:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.13' }
      - run: pip install "rendercv[full]==2.8"
      - run: rendercv render resume/base.yaml --design resume/design.yaml
             --output-folder out --dont-generate-html --dont-generate-markdown
      - run: test "$(ls resume/out/*.png | wc -l)" -eq 1   # hard one-page gate, like package.sh
      # + Drive upload + ntfy steps below
```
DOCX parity: `scripts/yaml_to_docx.py` (python-docx) also runs fine headless — the repo's documented remote-session flow already does this.

**Trigger + quota mechanics — verified.** A push from the mobile app, web UI, or REST API (PAT) is a normal push event and triggers `on: push` workflows; only events created with the workflow's own `GITHUB_TOKEN` don't re-trigger (no loop risk if the Action commits PDFs back) ([docs](https://docs.github.com/en/actions/using-workflows/triggering-a-workflow)). GitHub Free includes **2,000 Actions minutes/mo + 500MB artifact storage for private repos**, $0.006/min after ([billing docs](https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions)). A render job is ~1–2 min → even 30 edits/week ≈ 240 min/mo, well inside free.

**The Google Drive leg — the 2025 gotcha, confirmed from Google's own docs.** *"Service accounts don't have storage quota and can't own any files. Instead, they must upload files and folders into shared drives"* or use OAuth delegation ([Drive API error guide](https://developers.google.com/workspace/drive/api/guides/handle-errors)). In consumer My Drive the uploader owns the file, so **a service-account upload into a folder shared from a personal gmail now hard-fails** with "Service Accounts do not have storage quota. Leverage shared drives or use OAuth delegation instead" — reported across 2025–2026 ([n8n #26050](https://github.com/n8n-io/n8n/issues/26050), Feb 2026; [sa-drive #31](https://github.com/jsmaskeen/sa-drive/issues/31), enforcement referenced around an April 15, 2025 cutoff — *exact enforcement date uncertain; Google states the rule without a date*). Consequences: his existing gspread service account remains fine for **Sheets** (no storage consumed) but cannot upload the PDF; most marketplace "upload to Drive" actions are service-account-based and therefore broken for consumer Drive (e.g., [adityak74/google-drive-upload-git-action](https://github.com/adityak74/google-drive-upload-git-action), last pushed Mar 2025). Workarounds, ranked:

1. **User-OAuth refresh token via rclone** — uploads run *as Salman*, files owned by him, can target the real `Job Applications/` tree. Setup per [rclone Drive docs](https://rclone.org/drive/): create own OAuth client (Desktop type), set consent screen **publishing status = Production** — in "Testing" status refresh tokens expire after 7 days; in Production they persist (revoked only if unused ~6 months or >100 tokens/client) ([Google OAuth2 docs](https://developers.google.com/identity/protocols/oauth2)). Full `drive` scope is a *restricted* scope ([scope table](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)) — an unverified personal app shows a one-time scary consent screen, acceptable for personal use; the non-sensitive `drive.file` scope avoids that entirely but only sees folders the app created (PDF would land in a new rclone-owned folder, not the existing tree). Run in Actions via [AnimMouse/setup-rclone](https://github.com/AnimMouse/setup-rclone) (maintained, pushed Jan 2026) with `rclone.conf` in a repo secret.
2. **Apps Script web app** — `doPost` deployed "Execute as: Me" + access "Anyone"; the Action POSTs the PDF (base64) + a shared secret; the script writes via DriveApp so the **owner owns the file**, anywhere in his Drive ([Apps Script web apps](https://developers.google.com/apps-script/guides/web)). Zero OAuth client, zero token expiry, ~50 lines; slightly hacky but genuinely zero-maintenance for a ~100KB PDF.
3. Google Workspace + shared drive — solves it "properly" but adds a paid subscription for one feature; overkill.

**Phone feedback loop (his existing ntfy):** the Action can attach the rendered preview PNG to the push (ntfy.sh attachment limit 15MB, expires 3h) and set a `Click` header to the Drive folder; failures (YAML typo, `Pages != 1`) send an alert instead — a bad phone edit can never silently corrupt anything, it just fails CI ([ntfy publish docs](https://docs.ntfy.sh/publish/)).

## 3. Custom form-based editor (Vercel) — the UX upgrade path

- **Mechanics:** one-page Next.js app: GET `resume/base.yaml` via GitHub Contents API → render one field per bullet + drag-to-reorder (dnd-kit) → "Publish" PUTs the file back as a commit → the same render Action fires (API commits trigger push workflows — verified above). Round-trip fidelity: the [`yaml` npm package (eemeli)](https://eemeli.org/yaml/) "supports parsing, modifying, and writing YAML comments and blank lines" via its Document API — his commented YAML survives edits, so the repo diff is only the changed nodes (true zero-drift).
- **Auth:** fine-grained PAT scoped to the one repo (contents: read/write), **"no expiration" allowed for personal repos since Oct 2024** ([GitHub changelog](https://github.blog/changelog/2024-10-18-new-pat-rotation-policies-preview-and-optional-expiration-for-fine-grained-pats/)) — kept server-side in a Vercel env var; gate the page with a secret URL + password-cookie middleware (Vercel's built-in password protection is a paid feature; DIY is free and sufficient for one user).
- **Hosting:** Vercel Hobby free tier — 100GB transfer, ~1M function invocations/mo, non-commercial personal use allowed (2026 limits; *numbers via [Vercel docs](https://vercel.com/docs/plans/hobby) as summarized in current third-party roundups, e.g. [deploywise.dev](https://deploywise.dev/blog/vercel-free-tier-limits-2026) — not fetched from vercel.com directly*). Usage here is trivially small.
- **Effort/maintenance:** ~1–2 focused days to build (200–400 LoC); low ongoing (occasional dependency bumps; PAT never expires). It is, however, a fifth system to own — build it only after the GitHub-app flow proves annoying, and note it also creates a safe editing surface if the assistant ever needs one (she currently stays in Sheets).

## 4. Typst.app — reject

Typst.app now has **Git Sync** (bidirectional GitHub/GitLab, added recently): link a project to a repo, pull/push from the editor. But: it's **experimental** ("possible that you encounter bugs"), **entirely manual** (pull/push buttons — forget to push and you have drift, the exact failure mode to avoid), and linking requires **Typst Pro at $7.99/mo** ([git-sync docs](https://typst.app/docs/web-app/git-sync/), [pricing](https://typst.app/pricing/)). The disqualifier is architectural: Typst.app edits `.typ` files, but in a RenderCV pipeline the `.typ` is *generated output* — RenderCV's own maintainer confirms the YAML is the source and RenderCV ships its own Typst package it templates via Jinja2 (HN thread). Editing the `.typ` is overwritten on the next render and never flows back to YAML. Mobile support is undocumented and it's a desktop-class editor UI. Wrong layer, wrong sync model.

## Cross-cutting facts worth keeping

- rendercv 2.8 = current release (2026-03-21), **Python ≥3.12** (his automation repo's Python 3.11 doesn't matter — the render workflow installs its own 3.12/3.13).
- No SemVer: pin `rendercv[full]==2.8` everywhere; upgrade CI and Mac together, deliberately.
- Free GitHub plan covers the whole flow for $0; total new spend for the recommended path: $0 (Apps Script) or $0 + one-time OAuth setup (rclone).
- ATS/parse posture unchanged: rendering still happens through the same pinned engine + his design.yaml, so the 2026-07-07 parse verification remains valid — another reason to prefer options that reuse the repo's renderer over the hosted app's unknown engine version.

## RECOMMENDATION

Build the GitHub-native flow now and skip the rest: add a ~40-line Action to the existing private repo that fires on push to resume/**, installs "rendercv[full]==2.8" on ubuntu-latest (pure pip, fonts and Typst bundled — verified working in GitHub's cloud via the official rendercv-pipeline), runs the exact Makefile command, hard-fails unless the PNG count is 1, uploads the PDF to Drive, and pings his existing ntfy topic with the preview PNG attached and a click-through Drive link. For the Drive leg, do NOT reuse the Sheets service account — Google now gives service accounts zero storage quota so consumer My Drive uploads hard-fail; instead use either a ~50-line Apps Script doPost web app running as Salman (zero credentials to rotate) or rclone with his own OAuth client published to Production (token never expires). He edits from the GitHub mobile app (file → edit → commit, well under 2 minutes for a bullet tweak), the repo stays the single source of truth, a typo just fails CI with a phone alert, and total cost is $0 within GitHub's 2,000 free private-repo minutes. If raw-YAML-on-phone proves irritating after a couple of weeks, layer on the Vercel form editor (fields per bullet, drag reorder, no-expiry fine-grained PAT, comment-preserving yaml library) as a pure UX skin over the same pipeline. Avoid the RenderCV App as the system of record for now — its GitHub sync is backup-only (app becomes the source of truth), its engine version is unpinned against his v2.8 design, and its issue tracker shows open rendering bugs — but a free-account test is worth 15 minutes and it's worth rechecking in 6 months for true two-way sync. Typst.app is the wrong layer entirely (it would edit RenderCV's generated .typ output with manual pull/push sync) and should be dropped from consideration.
