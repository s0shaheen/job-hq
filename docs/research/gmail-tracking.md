# Auto-tracking job-application status from Gmail (2 consumer accounts) — July 2026

## 0. TL;DR architecture

Auto-forward everything from the assistant's alt Gmail to the owner's main Gmail (one-time, zero-maintenance), then run ONE Google Apps Script bound to the main account on a 15-minute trigger: deterministic sender/subject gate → Claude Haiku (`claude-haiku-4-5`) classification via UrlFetchApp → append event rows to a dedicated tab of the existing Google Sheet → Gmail label `JobTrack/Processed` for idempotency → ntfy push for interview/OA/recruiter events. The existing GitHub Actions + gspread job stays the "joiner" that matches event rows to application rows and a daily watchdog that alerts if the script's heartbeat goes stale. Details and evidence below.

---

## 1. Path (a): Google Apps Script bound to each account — VERIFIED

**Consumer (@gmail.com) quotas** (from https://developers.google.com/apps-script/guides/services/quotas):
- Triggers total runtime: **90 min/day** (Workspace: 6 hr/day)
- URL Fetch calls: **20,000/day**
- Email read/write (excluding send): **20,000/day**
- Script runtime: **6 min/execution**; simultaneous executions: 30/user; Properties read/write: 50,000/day
- Time-driven triggers can fire "as frequently as every minute" (https://developers.google.com/apps-script/guides/triggers/installable)

**Quota math for this workload:** at 30 applications/week, a 15-min trigger (96 runs/day) doing one `GmailApp.search` + a few message reads + 0–5 Haiku calls + 1–2 sheet appends runs ~5–30 s → **~10–50 min/day of trigger runtime, comfortably under 90**; UrlFetch usage is tens/day vs 20,000.

**Auth/verification reality (the big win of this path):**
- Gmail read scopes (`gmail.readonly`, `gmail.modify`, `gmail.metadata`, `gmail.settings.basic`) are **restricted** scopes; only `gmail.labels` is non-sensitive (https://developers.google.com/workspace/gmail/api/auth/scopes).
- But restricted-scope verification is **explicitly exempt for personal use**: "if you are the only user of your app or if your app is used by only a few users, all of whom are known personally to you" (https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification). Owner + assistant = exempt. You just click through the "unverified app" warning once per account.
- Apps Script's own docs: verification isn't required for scripts whose owner and users are the same account/domain; unverified scripts only face a warning screen + a user cap (https://developers.google.com/apps-script/guides/client-verification).
- Grant longevity: "Apps Script does not enforce the re-authentication frequency configured in Google Cloud... because Apps Script can run automatically using triggers, which operate without direct user interaction" (https://developers.google.com/apps-script/guides/services/authorization). Personal-script grants persist indefinitely; the 7-day token expiry (see path b) is a property of external OAuth clients in *Testing* status, not of a script the owner authorized for himself.

**Cross-account Sheet write (script in account A → Sheet owned by account B): YES.** Installable triggers run "as the person who created the trigger," and file access follows normal Drive permissions of that identity (https://developers.google.com/apps-script/guides/services/authorization). So the main-account script writes the existing Sheet if the Sheet owner shares it to the main account as Editor (same mechanism the gspread service account already uses). `SpreadsheetApp.openById()` simply throws if the executing user lacks permission (https://developers.google.com/apps-script/reference/spreadsheet/spreadsheet-app).

**Calling the Anthropic API from UrlFetchApp: YES.** Plain HTTPS POST to `https://api.anthropic.com/v1/messages` with `x-api-key` + `anthropic-version` headers works from Apps Script; requires only the `script.external_request` scope; store the key in Script Properties. Working community examples: gist "Use Anthropic's Claude API via Google Spreadsheets with AppScript" (https://gist.github.com/estevecastells/08ffa9064b57ab34a622dee16c32b629), key-management how-to (https://spreadsheet.dev/api-keys-openai-gemini-anthropic-apps-script), UrlFetchApp reference (https://developers.google.com/apps-script/reference/url-fetch/url-fetch-app). Anthropic even ships a "Google Apps scripter" prompt (https://docs.anthropic.com/en/prompt-library/google-apps-scripter).

**ntfy from Apps Script:** trivial — `UrlFetchApp.fetch("https://ntfy.sh/<topic>", {method:"post", payload:msg, headers:{Title:..., Priority:"4"}})`; no auth on ntfy.sh, topic name is the password (https://docs.ntfy.sh/publish/).

## 2. Path (b): Gmail API from GitHub Actions — VERIFIED, viable, second choice

**OAuth for consumer @gmail.com:**
- Testing-status gotcha confirmed verbatim: "A Google Cloud Platform project with an OAuth consent screen configured for an external user type and a publishing status of 'Testing' is issued a refresh token expiring in 7 days" (https://developers.google.com/identity/protocols/oauth2). Fix: publish the consent screen to **In production**. With restricted Gmail scopes the app is then "unverified" — users see a warning screen and a 100-account cap applies, but the personal-use exemption (above) means no CASA security assessment is ever needed for 2 accounts; tokens become long-lived.
- Refresh-token death causes (must design for): user revocation; **unused for 6 months**; **"the user changed passwords and the refresh token contains Gmail scopes"** (this is the silent killer for a job-search tool — password rotation on either account bricks the pipeline until re-consent); 100 live refresh tokens per account per OAuth client (oldest silently invalidated) (same URL).
- Token storage: refresh token + client id/secret as GitHub encrypted repo secrets; exchange for access tokens per run (standard `google-auth` flow). One secret set per account (main + alt) unless forwarding consolidates to one.

**Gmail API quota** (https://developers.google.com/workspace/gmail/api/reference/quota): 6,000 quota units/min/user (messages.list=5u, messages.get=20u, messages.modify=5u, history.list=2u) — irrelevant at this volume. Note: Google says exceeding quota "is planned to incur charges to your Cloud billing account later in 2026" — still a non-issue here.

**GitHub Actions cron reliability** (https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows): minimum interval 5 min; "can be delayed during periods of high loads... High load times include the start of every hour," and queued runs can be **dropped** at peak (schedule off-the-hour); scheduled workflows auto-disable after 60 days of inactivity **in public repositories only** — his repo is private, so not affected, but note schedules run only on the default branch. Budget note: a 1–2 min run every 30 min ≈ 1,500–2,900 min/month vs the Free plan's 2,000 included private-repo minutes (per GitHub's published plan limits; not re-verified this session) — hourly polling stays safely inside.

## 3. Path (c): auto-forward alt → main — VERIFIED, recommended as the consolidator

From https://support.google.com/mail/answer/10957:
- Add forwarding address in alt → Google sends a **verification link to the main inbox**; click once to activate.
- Forward-all: "We forward all new messages to the account, **except for spam**" — so a rejection mis-flagged as spam in the alt account silently never reaches main. Mitigation: in the alt account create a filter `from:(greenhouse.io OR greenhouse-mail.io OR ashbyhq.com OR myworkday.com OR lever.co OR icims.com OR smartrecruiters.com OR successfactors.com OR workablemail.com OR linkedin.com)` → "Never send to spam."
- Only **new** mail is forwarded (backfill must read the alt inbox directly once — see §7).
- Selective forwarding is possible via filters instead of forward-all; one filter per destination address. For a dedicated applications account, forward-all is simpler and catches unknown company no-reply domains that any allowlist would miss.
- Attribution survives forwarding: the original `To:` header still bears the alt address, so the pipeline can tag each event with which identity applied.

## 4. Path (d): open-source parsers worth stealing from + commercial proof

**Best-in-class: JustAJobApp/jobseeker-analytics** (198 stars, 83 forks, FastAPI + Next.js, Gmail API OAuth, formally approved by Google's data-safety review in March 2026) — https://github.com/JustAJobApp/jobseeker-analytics. Its filter config is public at `backend/email_query_filters/applied_email_filter.yaml`: two-tier logic (include = match any; exclude = match all). Included senders: `careers@*`, `ashbyhq.com`, `greenhouse.io`, `smartrecruiters.com`, `myworkday.com`, `linkedin.com`, `hire.lever.co`, plus niche ones; include-subjects: "application has been submitted", "confirmation of your application", "thank you for applying", "your application has been received", "interview", "assessment", "scheduling", "next steps"; excludes: "newsletter", "blog", "do you want to finish your application", "mock interview", senders `info@`, `support@`, `newsletter@`, `huntr.co`, `@interviewing.io` (from https://raw.githubusercontent.com/JustAJobApp/jobseeker-analytics/main/backend/email_query_filters/applied_email_filter.yaml). Company-name heuristic in `backend/utils/email_utils.py`: most-frequent capitalized word in body → else last capitalized words of subject when sender is a generic ATS domain → else sender domain. (LLM — Gemini — is used elsewhere in the app for analysis; the filter layer is deterministic.)

**Closest to Salman's stack: coolbrother/apply-potato** — https://github.com/coolbrother/apply-potato. Gmail API polling every 10 min, LLM classifier (`src/email_classifier.py` + `prompts/email_classification.txt`), **Google Sheets sync** (`src/sheets.py`), URL-based dedup (`src/deduplication.py`), detects "confirmations, OAs, interviews, offers, and rejections." Weakness for this use case: self-hosted on a local machine (Windows service / macOS LaunchAgent) — exactly the always-on-Mac dependency to avoid; steal its prompt + sheets/dedup patterns, not its deployment.

**Regex phrase library: Tomiwajin/CareerSync** — https://github.com/Tomiwajin/CareerSync. Pure pattern matching, stateless Next.js: Applied = "thank you for applying"/"application received"; Interview = "next steps"/"would like to invite you"; Rejected = "not selected"/"pursue other candidates".

**Commercial trackers as signal-proof:** Teal markets a job tracker with status stages, but its own Knowledge Base documents manual status updates + follow-up templates, not inbox scanning (https://help.tealhq.com/en/articles/9530119-job-tracker-guidance; third-party blogs claim Gmail scanning — **unconfirmed in Teal's own docs, treat as uncertain**). Huntr: board + Chrome-extension capture; no inbox auto-scan feature found. Careerflow: drag-and-drop tracker + extension capture from job boards; no automatic Gmail sync found (https://help.careerflow.ai/en/articles/8936777-changing-a-job-s-application-status). The products that *do* prove inbox-scanning works in 2026 are the newer wave: G-Track (https://jobtrack-ai.com/gmail-job-tracker), JobFlow AI (https://jobflow-ai.com/), SkillStory email-status-sync "auto-detect interview invites, rejections, and offers" (https://www.ourskillstory.com/features/email-sync), SkillSynchrony (scans every 10 min), and JobShinobi, which explicitly documents **forwarding-based** workflows (https://www.jobshinobi.com/blog/how-to-use-email-to-track-job-applications-automatically). Signals they all converge on: ATS sender-domain allowlist + subject phrases + AI for the ambiguous middle — validating the hybrid below.

**Not a threat/dependency:** Gmail's Jan-2026 Gemini-3 "AI Inbox" adds summaries/to-dos, not job-application tracking (https://blog.google/products-and-platforms/products/gmail/gmail-is-entering-the-gemini-era/).

## 5. Classification: hybrid (deterministic gate → Haiku), not either alone

- **Deterministic-only** (CareerSync-style) is cheap and auditable but brittle exactly where it matters: rejection wording varies wildly ("we've decided to move forward with other candidates", "keep your resume on file"), and recruiter outreach has no fixed vocabulary. jobseeker-analytics' Google-approved filter shows deterministic works well as a *relevance gate*, not as a *status oracle*.
- **LLM-only** wastes calls on newsletters/spam and creates an unauditable failure mode.
- **Hybrid (recommended):** Stage 1 Gmail query gate (senders + subject phrases from §4, ~zero false negatives on ATS mail; forward-all makes unknown company domains reachable via subject phrases + `careers@`/`no-reply@` heuristics). Stage 2: Claude **Haiku 4.5** (`claude-haiku-4-5`, $1/MTok in, $5/MTok out) on the gated set with truncated body (~2K tokens in, ~150 out, strict JSON: `{event_type: received|rejection|oa_invite|interview|recruiter_outreach|other, company, title, ats, job_url, confidence, evidence_quote}`). Cost ≈ $0.003/email → at 10–30 apps/week (~150–250 job emails/month incl. status mail) ≈ **$0.50–0.80/month**; a 90-day backfill of ~1,000 emails ≈ **$3**. Effectively free; "never breaks" is unaffected because a Haiku failure degrades to "logged, unclassified, retry next run."

## 6. Matching an email to a tracked job row

Layered, in confidence order: (1) **ATS job-id from links** in the email body — Greenhouse `boards.greenhouse.io/<company>/jobs/<id>`, Lever `jobs.lever.co/<company>/<uuid>`, Ashby `jobs.ashbyhq.com/<company>/<uuid>`, Workday requisition codes (JR-/R-#####) in subject/body, iCIMS tenant subdomain `<company>.icims.com` — matched against the job URL already captured at intake in `applications-log.csv` (apply-potato uses exactly URL-keyed dedup). Confirmation emails often omit links, so (2) normalized company (sender display name / domain / subject-tail heuristic from jobseeker-analytics) + fuzzy title vs open applications, scoped to rows applied in the last ~45 days; (3) no match → write the event row anyway with `match=NEEDS_REVIEW` for the assistant — never guess-update a status. Rejections should *suggest* status (separate column) rather than hard-overwrite, so a misread never destroys data.

## 7. Idempotency + 60–90-day backfill

- **Idempotency:** Gmail label `JobTrack/Processed`; the poll query is `newer_than:3d -label:JobTrack/Processed (<gate>)`. Label only AFTER the sheet append succeeds (crash-safe: at-least-once + dedupe on RFC822 `Message-ID` stored in a hidden sheet column — also dedupes the alt-copy/main-copy case if the assistant ever CCs). Labels via GmailApp (path a) or `messages.modify` at 5 quota units (path b).
- **Backfill:** same pipeline over `after:2026/04/14 (<gate>) -label:JobTrack/Processed`, paginated. Apps Script's 6-min execution cap → time-boxed chunks (~4 min/run, cursor in Script Properties), finishing ~1,000 emails over a day or two within the 90-min trigger budget. The **alt account's history** predates forwarding, so backfill must read alt directly once: either a temporary copy of the script bound to the alt account writing to the same shared Sheet, or a one-off OAuth client left in *Testing* status — the 7-day token expiry is irrelevant for a single-day, run-once backfill.

## 8. Recommended architecture (one inbox, one script, sheet-joined) + failure modes

1. Alt → main forward-all (keep alt's copy so the assistant's workflow is untouched) + "never send to spam" filter in alt.
2. Apps Script in main account, 15-min trigger: gate → Haiku → append to `Email Events` tab (shared-editor on the existing Sheet; that Sheet keeps single-writer-per-tab discipline: script owns `Email Events`, the GH Actions job owns status columns) → label → ntfy push (priority 4-5 for OA/interview/recruiter, quiet for confirmations/rejections).
3. Existing GitHub Actions Python (daily or on schedule): join `Email Events` → application rows via §6, write suggested statuses, and **watchdog** the script via a heartbeat cell the script updates every run — stale >2 h → ntfy alert. This is the mutual-monitoring that makes "never breaks" real: cron watches the trigger, the trigger's failure emails from Google watch the script.

**Failure modes, explicitly:** (i) alt spam swallows ATS mail pre-forwarding → mitigated by the alt-side filter, residual risk small; (ii) Google account password change: harmless for Apps Script grants, fatal for path-b refresh tokens — another reason (a) wins; (iii) Apps Script trigger errors → Google emails daily failure summaries to the owner + heartbeat watchdog catches silence; (iv) Anthropic outage → events logged unclassified, message left unlabeled, retried next run; (v) LLM misclassification → statuses are suggestions with `evidence_quote`, assistant confirms in the Sheet; (vi) interview invites that arrive only as calendar links still surface because the invite email itself is classified; (vii) GH Actions cron drift/drop affects only the joiner/watchdog cadence, never event capture; (viii) forwarding starts at setup time — historical alt mail handled by the one-off backfill; (ix) quota exhaustion is arithmetically out of reach at ≤30 apps/week.

**Uncertain/flagged:** Teal's inbox-scanning claim (third-party blogs vs silent official docs); GitHub free-minutes figure quoted from published plan limits without re-fetching; iCIMS/SuccessFactors exact sender addresses vary per tenant (`<company>@icims.com` / system domains) — the deterministic gate should treat them as domain-suffix matches and let forward-all + subject phrases catch stragglers.

## RECOMMENDATION

Consolidate to one inbox by auto-forwarding everything from the assistant's alt Gmail to the main account (one-time verified setup; add a never-send-to-spam filter for ATS domains in the alt account), then run a single Google Apps Script bound to the main account on a 15-minute trigger: deterministic sender/subject gate (patterns lifted from jobseeker-analytics' Google-approved filter), Claude Haiku 4.5 via UrlFetchApp for status classification (~$0.50-0.80/month), append-only rows to an Email Events tab of the existing Sheet, Gmail label for idempotency, and ntfy pushes for interviews/OAs/recruiter outreach. Apps Script is the "never breaks" choice for consumer accounts: no OAuth client, no refresh tokens, no verification (personal-use exemption for restricted scopes), grants that survive password changes, and quotas (90 min/day trigger runtime, 20K UrlFetch/day) that this workload uses under 5% of. Keep the existing GitHub Actions job as the joiner that matches events to application rows (ATS job-id from links first, fuzzy company+title fallback, NEEDS_REVIEW never guess) and as a heartbeat watchdog that ntfy-alerts if the script goes silent — the two systems monitor each other. Run the 60-90-day backfill once through the same pipeline (a temporary alt-bound script copy, or a throwaway Testing-mode OAuth token, since 7-day expiry is irrelevant for a one-off). Avoid building on the Gmail-API-from-Actions path as primary: it works (publish unverified to production to escape the 7-day testing expiry), but password changes silently revoke Gmail-scoped refresh tokens and cron can drift or drop - keep it documented as the fallback. Statuses land as suggestions with evidence quotes, so the assistant keeps working entirely in Sheets and a misclassification never destroys data.
